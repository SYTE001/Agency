### S1 — "Agency.timezone is only metadata; day windows use Node local time" — STALE

**Doc claim:** `docs/production-readiness.md` lines 67–85 and risk item B5 (line 251) state that day boundaries are computed by `startOfDay`/`endOfDay`/`daysAgoDate` helpers in `lib/services/common.ts` using the Node process's local time (`setHours(0,0,0,0)`), and that `Agency.timezone` exists but is "hanya metadata — belum dipakai dalam kalkulasi window laporan".

**Current-source proof this is no longer true:**

- `lib/services/common.ts` no longer contains any `startOfDay`, `endOfDay`, `daysAgoDate`, or `setHours` — grep across `lib/` and `app/` returns zero hits for these symbols. `common.ts` instead exports `getAgencyTimezone` (line 26), a cached lookup of the agency's IANA zone with `normalizeTimezone` fallback.
- A dedicated `lib/timezone.ts` provides tenant-zone boundary helpers: `dayStartInTz` (line 75), `dayEndInTz` (81), `daysAgoStartInTz` (85), `dateKeyInTz` (111), `startOfWeekInTz` (141), `monthStartInTz` (149), `parseDateTimeLocalInTz` (155) — all built on `calendarDateInTz` + `localToUtc` (lines 17–73).
- These helpers are actually used in reporting windows, i.e. the timezone is no longer "only metadata": `lib/services/overview.ts:3,44-47`; `lib/services/finance.ts:3,20-22`; `lib/services/reports.ts:3,8-14`; `lib/services/creators.ts:2`; `lib/services/brands.ts:2`. The overview page formats dates in the tenant zone (`app/(app)/overview/page.tsx:47-48`).
- Behavior is covered by `lib/timezone.test.ts` (boundary, month/year rollover, and DST-start cases).

**Residual truth in the doc:** the doc's recommendation to decide the deployment `TZ` is obsolete for report windows; only A13 (DST-day `dayEndInTz`) remains as an open timezone defect, and it is a different, narrower bug than the one described.

### S2 — "Search uses bare `contains` without `mode: "insensitive"` in 7 files" — STALE

**Doc claim:** `docs/production-readiness.md` §8.1 (lines 186–194), risk item B4 (line 250) and migration step 5 (line 269) state that search uses `{ contains: q }` without `mode: "insensitive"` in `creators.ts`, `brands.ts`, `campaigns.ts`, `products.ts`, `tasks.ts`, `content.ts`, `search.ts`, and that a PG migration would make search case-sensitive until a 7-file mechanical fix lands.

**Current-source proof this is no longer true:**

- All those files now route through the shared helper `containsInsensitive` defined at `lib/services/common.ts:36-38`, which returns `{ contains: q, mode: "insensitive" }` on PostgreSQL and `{ contains: q }` only on SQLite (where SQLite `LIKE` is already ASCII case-insensitive):
  `lib/services/brands.ts:41`, `lib/services/creators.ts:56-57`, `lib/services/campaigns.ts:49`, `lib/services/tasks.ts:22`, `lib/services/products.ts:61`, `lib/services/content.ts:37`, and `lib/services/search.ts:33,39,45,51,57,63,76`.
- Grep confirms **zero** remaining bare `contains:` filter usages outside the helper itself.
- Therefore B4 ("`contains` jadi case-sensitive di PG") is resolved for the listed files; migration step 5 is already done.

**Residual nit (not the doc's claim):** on SQLite the helper omits `mode`, so matching is case-insensitive only for ASCII; non-ASCII (e.g. Indonesian text beyond ASCII is fine, but any user-entered non-ASCII) may behave differently between providers. This is a parity footnote, not the claimed blocker.
